- **A REST `GET` cannot carry a trace_id** (2026-11-03, #24): `rest_translation::read_body_for_method` forwards `{}` for every `GET`, and query parameters are not mapped, so any RPC called by `GET` on its REST route (the streaming routes allow `GET` too) always reaches the backend with an empty `trace_id`; only a `POST` body can set it. Mapping a `traceId` query parameter (or an inbound trace header) onto field 200 would let browser `GET`s be traced. New behaviour: a `feature`, needs design.
- **MCP session frames have no trace_id** (2026-11-03, #24): `sys.mcp.McpRequest` (every `Broker*McpSession` route the gateway proxies) declares no field 200, so no MCP session through the gateway can be traced, and none could be covered by #24's WebSocket test (it uses `oauth.Session/BrokerSession`, whose `SessionRequest` has one). The message is tacplus' (`sys/mcp.proto`), so the change is there.
- **A generated flag for the MCP carrier** (2026-11-07, #15): the gateway recognises a service's MCP session carrier by the method name tacplus generates for it (`Broker<Service>McpSession`, client- and server-streaming; `proxy_grpc::is_mcp_carrier`), since `RouteInfo` says nothing about the request type. A generated `RouteInfo.mcp_carrier: bool` (or the request type's full name) would make that a fact of the registry, not a naming convention; `e2e_mcp_tenant`'s registry test catches a rename today. The change is in tacplus' Rust rest_dispatch generator.
- **Drop the ROADMAP "Later" item "Keep the Let's Encrypt certificate across a kernel restart"** (2026-11-03, #25): the gateway no longer reads LetsEncryptState at all; its certificate is in its own config, delivered by kernel's system-config refresh and put there by the deployment's pipeline (tacplus-dev/roadmap:decisions/certificates-by-pipeline-2026-11-03.md), so there is nothing of letsencrypt's left to keep. Jody's file, so only a proposal here.

New behaviour: a `feature`, needs design.

- **HTTP/3 (QUIC) is promised, never served** (2026-11-14, nightly scan): README.md ("axum server (HTTP/1.1 + HTTP/2 + H3)", the Configuration table's `enable_http3` "Enable QUIC/HTTP3 listener" and `quic_listener`) and `proto/services/gateway.proto`'s `Config` (`enable_http3`, `quic_listener`, both defaulting on) describe a QUIC listener, but nothing opens one: `src/main.rs` logs `enable_http3` (line 133), counts it in the "at least one of enable_http, enable_http3, or enable_grpc" check (line 160) and never reads `quic_listener`; `Cargo.toml` and `src/` have no `quinn`, `h3` or QUIC dependency (the lock's `quinn` comes in through reqwest, via the generated crates). Either serve HTTP/3 (new behaviour: a `feature`, needs design, and a reuse argument against staying on HTTP/2) or take the promise out: README's architecture line and table rows, and the proto comments (the fields stay for wire compatibility, marked unimplemented). - **idp_proxy forwards the hop-by-hop headers blob_proxy strips** (2026-11-15, nightly scan): `IdpProxy::proxy_request` (src/idp_proxy.rs:128-134 and 156-158) copies every request and response header except `Host` onto the Keycloak hop, including `connection`, `keep-alive`, `te`, `transfer-encoding`, `trailer` and `upgrade`. `blob_proxy::forwardable` (src/blob_proxy.rs:326) drops exactly those on its hop, and its comment says why: "forwarding them is how a proxy ends up advertising a framing or a keep-alive the next hop did not agree to". The IdP hop re-frames both bodies (the request is collected into a `Full`, the response streamed by hyper), so a forwarded `transfer-encoding` or `connection` describes the wrong connection. Fix, bug-sized: reuse `forwardable` (make it `pub(crate)`) for both directions in idp_proxy, keeping `Host` set to the backend and the `X-Forwarded-*` headers as they are. No failure observed; found by reading for trace propagation. Filed as #44 and fixed there (2026-11-20): both directions now go through `forwardable`.
- **The security checks should scan the image the gateway ships, not the names its Dockerfiles build FROM** (2026-11-17, nightly scan; #38, #40): looper-scan's `base_images` runs `trivy image` on every `FROM` reference by name. Two results follow. The scan also misses a shipped binary that comes from an image used only through `COPY --from=<image>` (no `FROM`): `ghcr.io/grpc-ecosystem/grpc-health-probe:v0.4.60`'s probe carries two HIGHs (CVE-2026-116587 go-jose, CVE-2026-78661 x/net) that no build report lists. New behaviour for tacplus-dev/looper: a `feature`, needs design and a looper ROADMAP entry.
- **The security report should list HIGH and CRITICAL findings that are no longer new** (2026-11-18, nightly scan; #43): `summary.md` lists only findings that are "failing the policy" or "new since the previous run". A HIGH with no fixed version is not blocking, so once it has been seen in one run it drops out of both lists and is visible only in `findings.json`. That is how osv-scanner's GHSA-fc5q-39xc-vjpf (picomatch 4.0.7, HIGH, `webapp/package-lock.json`, `new: false`) went unfiled until this scan's own osv-scanner run found it (#43). A "Standing HIGH/CRITICAL, neither baselined nor excepted" section in the summary would keep them in front of the scan, and of whoever reads the report. Severity is not the whole gap. A finding first seen in a run that no scan files from (a land's or a `--build`'s report) is already `new: false` in the next nightly, so it gets filed at no severity: chrono's RUSTSEC-2026-0543 (UNKNOWN, cargo-deny and osv-scanner) went unlisted that way until the 2026-11-20 scan found it in `findings.json` (#31). The same holds for mailbox#22. Marking `new` against the last *nightly* report rather than the previous run, or a "not yet filed" list, would close it. New behaviour for tacplus-dev/looper (looper-scan's summary): a `feature`, needs design and a looper ROADMAP entry.
- **`forwardable` ignores the headers `Connection` names** (2026-11-20, #44): RFC 9110 §7.6.1 makes every header listed in a `Connection` value hop-by-hop too (`Connection: close, X-Foo` means `X-Foo` describes this connection), and a proxy is to drop them along with the fixed list. `blob_proxy::forwardable` (now used by both the blob and the IdP hop) drops only its fixed list, so such a header still crosses. Fix, small: read the `Connection` values first and filter those names as well, with a test in blob_proxy. No failure observed.

- **Take `rotation.Envelope` from the generated model once the floor is 2.7** (2026-11-17, #26): `src/rotation.rs` declares `rotation.Envelope` by hand, as `TraceProbe` does, because the tacplus 2.6 line (pinned 2.6.13) generates no `sys/rotation.proto` types into the gateway's model; the proto is on tacplus main (tacplus#322) and first ships in 2.7. - **Rotating streams cannot be tested end to end against a generated backend yet** (2026-11-17, #26): `e2e_rotation.rs` stands in for the backend's `<Svc>Rotating` sibling. Generated servers serve the sibling only for S2S services (tacplus `rustServesRotatingSibling`: `IsS2S`), and C2S rotation, with its clients, is tacplus-dev/tacplus#323. Once #323 generates the C2S sibling and a client, a test with the generated server and client through the gateway would pin both ends to one wire. Note one difference: the generated server refuses an unknown session with `PERMISSION_DENIED`, while the gateway answers `UNAUTHENTICATED`, as #26 asks.
- **The gateway's session table is per process** (2026-11-17, #26): a rotation opens on the same HTTP/2 connection as the leg it replaces (tacplus#322), so it reaches the same gateway replica, and the table lives in that process. A client that reconnects to rotate (a new connection, possibly through another replica behind a load balancer) gets `UNAUTHENTICATED`, and its stream ends as any unrotated stream does. Carrying the instance in the session id itself, sealed by the backend, would lift that; it is a change to tacplus' wire (tacplus-dev/tacplus#323's to decide).
- **Pin a tenant instance's TLS identity to the routed tid** (2026-11-15, #3): the gateway now dials `<svc>-<tid>` for a call naming tenant `<tid>`, but `Resolver::tls_verifier` narrows the backend certificate to the bare service label only (`expect_service(service_id)`), so any tenant's instance of that service would pass the handshake if the health index ever named the wrong endpoint. The instance's own backstop (`check_routed_tenant`, PERMISSION_DENIED for another tid) catches it after the hop. Verifying `spiffe://<td>/tenants/<tid>/services/<svc>` at the handshake would refuse it before any byte is sent; it needs a generated `SpiffeServerCertVerifier` that can also expect a namespace (tacplus). New behaviour: a `feature`, needs design.
- **Confirm: an MCP session's tenant is the token's `tid` claim** (2026-11-22, #3 with #15): #15 stamped a tenant-owned carrier's `McpRequest.tenant` with the tenant segment of the token's namespace and routed by it; #3 routes by tid (instances are `<svc>-<tid>`, kernel#23), and user and session token namespaces name the tenant by name (roadmap decisions/tenant-routing-2026-10-26.md, addendum 2026-10-28). So #3 stamps the verified token's `tid` claim (`GatewayAuth::caller_tid`, the claim `Subject` already binds rotations to) and routes the carrier by that stamped first frame through `route_stream`; a token with no `tid` (a `/system` caller, or a tenant namespace alone) is refused PERMISSION_DENIED. That rests on kernel putting `tid` on every token that opens an MCP session; if the hub wants another source (a tid in the namespace, a kernel lookup), only `caller_tid` changes.
- **Rotation of a tenant-routed stream** (2026-11-22, #3 with #26): a rotating sibling's opening leg is dialled on its first envelope, which carries a session id and no request, so the gateway has no target tenant for it before the dial, and since #3 it never takes one from the token. So the sibling of a method with a route field is refused `UNIMPLEMENTED` (`rotation::handle`), except an MCP session carrier's, whose tenant is the token's (#15) and the client falls back to the plain method, routed by its first message: tenant-owned streams do not rotate through the gateway. Lifting it needs the opening envelope to name its target tenant (a field of `rotation.Envelope`, or the gateway holding the leg until its first payload, which the generated client sends only after the backend's session id): tacplus' wire, tacplus-dev/tacplus#323's to decide. No fleet stream needs it yet (generated servers serve the sibling for S2S only).
- **Pin the grpc-health-probe image by digest too** (2026-11-22, #42): the hub's rule on #42 and #39 (2026-11-17) is to pin every base by digest and move the digest when the base has fixes. #38 pins `debian:trixie-slim` and #40 deletes `Dockerfile.cross`, but `Dockerfile` still copies `grpc_health_probe` from the tag `ghcr.io/grpc-ecosystem/grpc-health-probe:v0.4.60`, which can be re-pushed under the same tag. Pin it as `v0.4.60@sha256:...` once #38 has landed (its change sits on the adjacent lines), or drop the binary if no probe uses it (the launcher watches gRPC health itself).
- **The SPIFFE-path fallback never dials the SPIFFE path's endpoints** (2026-11-11, #32): README.md says a path no route claims is used "as a SPIFFE service path for endpoint resolution", and STATE.md lists the fallback as working. But `rest_translation::fallback` uses `get_endpoints_by_spiffe_path` only as a gate. It then hands the request path to `dispatch_via_proxy` as the gRPC method, so `request_json_to_proto` and `proxy_grpc::handle` accept it only when it is a ROUTES `grpc_path`. `handle` then dials that route's `service_id`, not the endpoints the SPIFFE index found. The indexed paths (`extract_spiffe_service_path`, e.g. `seatrials/services/kernel` or `mud-controller/agent-42`) are never gRPC paths, so in practice no SPIFFE-routed request reaches a backend. #32's test can drive the branch only by indexing a gRPC path (`kernel.UserMint/MintDelegateOfflineToken`) as a SPIFFE path. What a SPIFFE-path request should carry (which method, which message type to map the JSON to) needs design. Until then, either retire the branch and correct README/STATE, or make it route to the indexed endpoints for a named method.
