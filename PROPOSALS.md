- **webapp-login: forget an add that never left** (2026-10-29, #17): `SignIn.startAdding` sets `tp-login-adding` (and the step-up tenant) in sessionStorage before the redirect, and nothing clears it if the redirect fails. Since #17 the page stays put with an inline error after a failed redirect. If the person then signs out and signs in again in the same tab, `complete()` treats that fresh sign-in as an add. Fix: in `startAdding`, clear both keys when `start` throws (bug-sized; flow.ts).
- **Unmaintained crates `cargo audit` still warns about** (2026-10-30, #20): after the aws-lc-rs relock there are no vulnerabilities, but four unmaintained warnings remain: `backoff` 0.4 and its `instant` (RUSTSEC-2025-0012, RUSTSEC-2024-0384; via the generated `httpclient` chassis), `serde_yaml` 0.9's `unsafe-libyaml` (RUSTSEC-2024-0449; via the generated types crate) and `rustls-pemfile` 2 (RUSTSEC-2025-0134; via `axum-server`, the generated model and the gateway itself). The first two belong upstream in tacplus' Rust chassis; `rustls-pemfile` the gateway can drop by parsing PEM with `rustls-pki-types`' `PemObject`. Since 2026-10-01 a fifth: `pin-utils` 0.1.0 (RUSTSEC-2026-0441), whose only path in is `hyper` 1.8.1 (`cargo tree -i pin-utils`); `hyper` 1.12.0 no longer depends on it, so a lockfile-only `cargo update -p hyper` should clear it (nightly scan, 2026-11-05). The build's security checks now report all five as new findings: tracked as the bug #31 (nightly scan, 2026-11-11).
- **One shared harness for the end-to-end tests** (2026-11-03, #23): `e2e_user_mint.rs`, `e2e_form_post.rs` and `e2e_mint_trace.rs` each carry their own copy of `unused_verifier()`, the plaintext `ProxyState` wiring and a "serve this stand-in on a real port" helper. A `#[cfg(test)] mod e2e_harness` holding them would cut ~40 lines a file and make the next stand-in (each trace-propagation test needs one, looper#51) a few lines. Not done in #23 so as not to collide with #24, which reworks `e2e_user_mint.rs`'s harness. Since #24, `e2e_stream_trace.rs` is a fourth copy, and it and `e2e_user_mint.rs` each define the same do-nothing `KernelMinter` (`NoMinter`) to build a REST router.
- **A REST `GET` cannot carry a trace_id** (2026-11-03, #24): `rest_translation::read_body_for_method` forwards `{}` for every `GET`, and query parameters are not mapped, so any RPC called by `GET` on its REST route (the streaming routes allow `GET` too) always reaches the backend with an empty `trace_id`; only a `POST` body can set it. Mapping a `traceId` query parameter (or an inbound trace header) onto field 200 would let browser `GET`s be traced. New behaviour: a `feature`, needs design.
- **MCP session frames have no trace_id** (2026-11-03, #24): `sys.mcp.McpRequest` (every `Broker*McpSession` route the gateway proxies) declares no field 200, so no MCP session through the gateway can be traced, and none could be covered by #24's WebSocket test (it uses `oauth.Session/BrokerSession`, whose `SessionRequest` has one). The message is tacplus' (`sys/mcp.proto`), so the change is there.
- **Drop the ROADMAP "Later" item "Keep the Let's Encrypt certificate across a kernel restart"** (2026-11-03, #25): the gateway no longer reads LetsEncryptState at all; its certificate is in its own config, delivered by kernel's system-config refresh and put there by the deployment's pipeline (tacplus-dev/roadmap:decisions/certificates-by-pipeline-2026-11-03.md), so there is nothing of letsencrypt's left to keep. Jody's file, so only a proposal here.
- **One certificate for every hostname now** (2026-11-03, #25): letsencrypt mode served a certificate per hostname by SNI; `cert_chain` serves one chain to every name, so `external_cert_pem` has to cover each `external_hostnames` and `web_bundles` hostname (the decision's wildcard plus apex does). Nothing checks that coverage at load; a check that refuses (or warns about) a certificate missing one of `external_hostnames` would catch a wrong secret version before browsers do. New behaviour: a `feature`, needs design.
- **HTTP/3 (QUIC) is promised, never served** (2026-11-14, nightly scan): README.md ("axum server (HTTP/1.1 + HTTP/2 + H3)", the Configuration table's `enable_http3` "Enable QUIC/HTTP3 listener" and `quic_listener`) and `proto/services/gateway.proto`'s `Config` (`enable_http3`, `quic_listener`, both defaulting on) describe a QUIC listener, but nothing opens one: `src/main.rs` logs `enable_http3` (line 133), counts it in the "at least one of enable_http, enable_http3, or enable_grpc" check (line 160) and never reads `quic_listener`; `Cargo.toml` and `src/` have no `quinn`, `h3` or QUIC dependency (the lock's `quinn` comes in through reqwest, via the generated crates). Either serve HTTP/3 (new behaviour: a `feature`, needs design, and a reuse argument against staying on HTTP/2) or take the promise out: README's architecture line and table rows, and the proto comments (the fields stay for wire compatibility, marked unimplemented). Jody's call which; the second is a doc-sized bug.
- **idp_proxy forwards the hop-by-hop headers blob_proxy strips** (2026-11-15, nightly scan): `IdpProxy::proxy_request` (src/idp_proxy.rs:128-134 and 156-158) copies every request and response header except `Host` onto the Keycloak hop, including `connection`, `keep-alive`, `te`, `transfer-encoding`, `trailer` and `upgrade`. `blob_proxy::forwardable` (src/blob_proxy.rs:326) drops exactly those on its hop, and its comment says why: "forwarding them is how a proxy ends up advertising a framing or a keep-alive the next hop did not agree to". The IdP hop re-frames both bodies (the request is collected into a `Full`, the response streamed by hyper), so a forwarded `transfer-encoding` or `connection` describes the wrong connection. Fix, bug-sized: reuse `forwardable` (make it `pub(crate)`) for both directions in idp_proxy, keeping `Host` set to the backend and the `X-Forwarded-*` headers as they are. No failure observed; found by reading for trace propagation. Filed as #44 and fixed there (2026-11-20): both directions now go through `forwardable`.
- **The security checks should scan the image the gateway ships, not the names its Dockerfiles build FROM** (2026-11-17, nightly scan; #38, #40): looper-scan's `base_images` runs `trivy image` on every `FROM` reference by name. Two results follow. A builder stage's base is reported as if it shipped: `Dockerfile.cross`'s `rust:trixie` accounts for 2695 of the 2921 findings and 108 of the 114 policy failures (#40), though only the binary leaves that stage. And a Dockerfile's own `apt-get upgrade` is invisible: the report keeps listing `debian:trixie-slim`'s zlib1g CVE-2026-85091 after the image has the fixed `1+deb13u1` (#38; tacplus-dev/llmproxy#62's acceptance has the same gap). Scanning the final stage as built (`trivy image` on the build's own image, or `trivy rootfs` over its filesystem, as tacplus-dev/looper#147 does for release jars), or at least skipping a base whose stage is only `COPY --from`'d, would make the report match what ships. The scan also misses a shipped binary that comes from an image used only through `COPY --from=<image>` (no `FROM`): `ghcr.io/grpc-ecosystem/grpc-health-probe:v0.4.60`'s probe carries two HIGHs (CVE-2026-116587 go-jose, CVE-2026-78661 x/net) that no build report lists. A by-hand trivy run in the nightly scan found them (2026-11-19, #33). Scanning the final stage as built would cover it too. New behaviour for tacplus-dev/looper: a `feature`, needs design and a looper ROADMAP entry.
- **The security report should list HIGH and CRITICAL findings that are no longer new** (2026-11-18, nightly scan; #43): `summary.md` lists only findings that are "failing the policy" or "new since the previous run". A HIGH with no fixed version is not blocking, so once it has been seen in one run it drops out of both lists and is visible only in `findings.json`. That is how osv-scanner's GHSA-fc5q-39xc-vjpf (picomatch 4.0.7, HIGH, `webapp/package-lock.json`, `new: false`) went unfiled until this scan's own osv-scanner run found it (#43). A "Standing HIGH/CRITICAL, neither baselined nor excepted" section in the summary would keep them in front of the scan, and of whoever reads the report. Severity is not the whole gap. A finding first seen in a run that no scan files from (a land's or a `--build`'s report) is already `new: false` in the next nightly, so it gets filed at no severity: chrono's RUSTSEC-2026-0543 (UNKNOWN, cargo-deny and osv-scanner) went unlisted that way until the 2026-11-20 scan found it in `findings.json` (#31). The same holds for mailbox#22. Marking `new` against the last *nightly* report rather than the previous run, or a "not yet filed" list, would close it. New behaviour for tacplus-dev/looper (looper-scan's summary): a `feature`, needs design and a looper ROADMAP entry.
- **`forwardable` ignores the headers `Connection` names** (2026-11-20, #44): RFC 9110 §7.6.1 makes every header listed in a `Connection` value hop-by-hop too (`Connection: close, X-Foo` means `X-Foo` describes this connection), and a proxy is to drop them along with the fixed list. `blob_proxy::forwardable` (now used by both the blob and the IdP hop) drops only its fixed list, so such a header still crosses. Fix, small: read the `Connection` values first and filter those names as well, with a test in blob_proxy. No failure observed.

- **Start the release image in a gate** (2026-11-09, #29): the image now runs as 65532:65532, and `just gates` checks the Dockerfiles' last `USER`, but nothing starts the image: a future path the gateway writes (a cache, a socket) or a file it reads that is not world-readable would only fail in a pod. A smoke step that builds the image and runs `launcher` as 65532 with a minimal config until `/healthz` answers would catch it; it needs a container runtime in the build job.
